# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Mr. Momo (the repo and some internal names still say "ro-yan" / "royan", its first name) — a pickup-only food ordering web app for a single fast-food stall. Customers browse a menu, order from their phone after logging in with an emailed code or Google (cash on pickup, no online payment), and track status. The stall owner uses an admin dashboard with real-time (WebSocket) new-order alerts and stock toggles. `docs/SPEC.md` holds the locked product decisions and the explicit v1/v2 scope split — read it before adding features, since much is deliberately out of scope.

## Commands

Backend (FastAPI, from `backend/`):
```
pip install -r requirements-dev.txt            # requirements.txt = prod only (Render)
uvicorn app.main:app --reload --port 8000     # runs on SQLite, dev OTP, no env vars needed
python -m pytest tests/ -q                     # full suite
python -m pytest tests/features/orders/test_orders.py::test_order_price_snapshot   # single test
python -m pytest tests/features/orders              # one feature (works from any folder: see pytest.ini)
```

Frontend (Vite + React, from `frontend/`):
```
npm install
npm run dev        # http://localhost:5173 (calls the backend at http://localhost:8000 unless VITE_API_URL is set; no Vite proxy)
npm run build
```

Dev conveniences: OTP is `123456` for any email when `OTP_DEV_MODE=true` **and** `ENV` is not production (real 6-digit code is also logged to the backend console when SMTP isn't configured). Admin is the owner email — logging in with `ADMIN_EMAIL` opens the admin dashboard; there is no separate admin password. Deployment is Render (backend, external Neon Postgres, see `render.yaml`) + Vercel (frontend); see `docs/DEPLOY-STEPS.md`.

## Backend folder layout (`backend/app/`)

Feature-based. `main.py` builds the app (startup, CORS, failure log) and mounts `router.py`, which includes every feature's router. Each feature is a folder in `features/` holding its `<name>_router.py` (routes), `<name>_service.py` (logic other files call) and `<name>_schemas.py` (Pydantic request bodies): `auth` (+ `otp_service.py`), `profile`, `menu` (`menu_router` public, `menu_admin_router` owner, `menu_seed.py`), `orders` (`orders_router` customer, `orders_admin_router` owner, `orders_service.py`: `order_payload`, `ORDER_LOAD`, `announce`, `notify_ready`), `feedback`, `store` (`store_service.py`: `accepting_orders`, `PAUSED_MESSAGE`), `reports`, `notifications` (`push_service.py`), `live` (WebSockets), `health`. Owner routes go in a separate `*_admin_router.py` when a feature has both sides. `middleware/failure_log.py` is the t_log middleware. `shared/` holds what many features use: `database.py`, `models.py` (all tables — they reference each other, so they stay in one file), `auth.py`, `clock.py`, `config.py` (`CORS_ORIGINS`), `mailer.py`, `request_log.py`, `validation.py`, `ws_manager.py`. Use absolute imports (`from app.shared.models import Order`). Routes call services through the module (`otp_service.send_otp`, `push_service.notify_admins`) so tests can monkeypatch them there; `MAX_ACTIVE_ORDERS` is in `features/orders/orders_router.py`. The Render start command is unchanged (`uvicorn app.main:app`). A new feature = a new folder + one line in `router.py`. `tests/` mirrors `app/`: `tests/features/<feature>/test_*.py`, `tests/shared/`, `tests/middleware/`, with fixtures and helpers (`login`, `make_item`, `place`, `my_order`, `bearer`) in `tests/conftest.py`. Test file names must be unique across folders (pytest's default import mode).

## Architecture

**Two independent apps, one JSON+WebSocket API.** No shared code between `frontend/` and `backend/`; the contract is the REST endpoints in `backend/app/features/*/*_router.py` (mounted by `app/router.py`; `main.py` only builds the app) and the WS message shapes below. Frontend routes `/` (customer) and `/admin` are both served from one SPA (`frontend/src/main.jsx`); `vercel.json` rewrites all paths to `index.html` so `/admin` works on refresh.

**One auth model, two privilege levels** (`backend/app/shared/auth.py`):
- Everyone logs in with email + 6-digit OTP, or with Google (`POST /api/auth/google`) → JWT, returned in the response body. The frontend stores it in `localStorage` and sends `Authorization: Bearer` (`frontend/src/services/api.js`). **Bearer-only — there is no auth cookie** (no CSRF surface, no `allow_credentials`). Tokens last 30 days (owner: 7).
- Admin is *not* a separate account: `require_admin()` checks the token's email is in `ADMIN_EMAILS` (configured via `ADMIN_EMAIL` env var); the admin WebSocket passes the same JWT as `?token=` (`ws_session(token, admin=True)`); `/ws/admin` and `/ws/me` close with 4401 when that token expires, and `useSocket` then stops reconnecting and calls `onReconnect` once so the caller's refetch gets the 401 and logs out. Logging in as the owner email *is* being admin (by OTP or Google). A logged-in non-owner gets **403** from admin endpoints, an invalid/missing token 401 — the frontend logs out only on those, never on network errors or 5xx (the free-tier backend returns 502 while waking up). The owner sees customers' full emails; customers only ever see masked ones (`order_payload(o, admin=...)`).
- **Google login** (`auth.verify_google_token`) is **off (404) unless `GOOGLE_CLIENT_ID` is set** — never verify with no audience: that accepts a Google token issued to *any* site, letting it log in here as its users (including the owner). The token must also come from Google's issuer and have `email_verified` true (missing = unverified). The frontend gets the client ID only from `/api/auth/mode` (no `VITE_` copy), so the button can't show while the backend refuses. A Google login for an existing email reuses that customer. Tests fake `id_token.verify_oauth2_token` (`tests/features/auth/test_google_login.py`).
- **Production guard**: `auth.check_prod_config()` runs in the app lifespan and aborts startup when `ENV=production` and `JWT_SECRET` is the default or `< 32` chars. `OTP_DEV_MODE` is forced off in production, and the menu is not auto-seeded there (`SEED_MENU` overrides).

**WebSockets — three channels** (`backend/app/shared/ws_manager.py`, single in-process `ConnectionManager`):
- `/ws/admin?token=` — the owner's JWT; receives `{type: "new_order", order}` (full email) and `{type: "status", ...}`. Drives the sound + visual alert.
- `/ws/me?token=` — the logged-in customer's channel (close 4401 on a missing/invalid token); receives `{type: "status", order_id, status}` for **all** of their orders, on every screen. Empty pools are dropped on disconnect. There is no per-order socket — the customer's orders come from `GET /api/orders/mine` and this channel patches them.
- `/ws/menu` — every client's menu; receives `{type: "availability", item_id, is_available}` for instant out-of-stock updates.

Because the manager is in-process, **this only works on a single backend instance** (`render.yaml` pins `--workers 1`; would break if scaled horizontally). Frontend sockets go through `src/hooks/useSocket.js`, which auto-reconnects and calls `onReconnect` so callers refetch what they missed.

**Money is stored as integer rupees, never floats.** `OrderItem.price_at_order` is a snapshot taken when the order is placed and is never recomputed — changing a menu price does not alter past orders (tested in `test_order_price_snapshot`). Order totals are summed from these snapshots.

**Order numbering resets daily (IST).** `order_number` is "count of orders since IST midnight + 1", so it restarts at 1 each day and is *not* unique across days (the DB `id` is the stable key). All time goes through `backend/app/shared/clock.py`: `utcnow()` (naive UTC, what the DB stores) and `today_start()` (IST midnight as naive UTC). Never call `datetime.utcnow()` directly. `create_order` is deliberately `async def` with no `await` between counting and committing, which makes numbering atomic on one worker — don't turn it into a plain `def`.

**Status is a forward-only ladder:** `placed → preparing → ready → completed` (`ORDER_STATUSES` in `backend/app/shared/models.py`, also used to validate `StatusIn`). The API rejects any move that isn't strictly forward (`set_status` in `features/orders/orders_admin_router.py`). The frontend copy is `STATUSES` in `frontend/src/config/constants.js` — keep them in sync. **`cancelled` is off the ladder** (`CANCELLED` in `shared/models.py`): a customer may cancel only while `placed` (`POST /api/orders/{id}/cancel`), the owner while `placed`/`preparing`; cancelled and completed orders never move again, and cancelled orders are excluded from the daily stats. **`not_collected` is off the ladder too** (`NOT_COLLECTED`; owner only, only from `ready`): the customer never picked it up, so it closes with **no cash** and isn't "to collect" any more; the customer sees "Not collected" in My orders, gets **no push/email**, and can't rate it. Closed statuses are `CLOSED` in `shared/models.py` (`completed`, `cancelled`, `not_collected`) — use it for every "unfinished" query; the frontend copy is `CLOSED`/`isActive` in `constants.js`. Every status change goes through `announce()` (customer channel + admin channel). Moving to `ready` also emails the customer via a `BackgroundTasks` job (`notify_ready`) that never raises.

**Failure log (`t_log` table).** `app/shared/request_log.py` + the `log_failures` middleware and exception handlers in `app/middleware/failure_log.py` write one row per failed request (status ≥ 400 — including rejected CORS preflights — and unhandled exceptions, which return a generic 500) and per failed background task (`method="TASK"`): method, path (no query string), status, duration, `error` (message plus the underlying cause, e.g. `Could not send the email… | TimeoutError: timed out`, or the traceback tail for crashes), client IP (first `X-Forwarded-For`), `Origin`, user agent, and the user's email from the bearer token. Successful requests are not logged; bodies, tokens and submitted values (422s keep field names only) never are. Rows older than 30 days are pruned at startup, and a logging failure never breaks a request. Read it with SQL (Neon console or a script): `SELECT created_at, method, path, status, error FROM t_log ORDER BY id DESC LIMIT 20;`. Don't add fields that could hold secrets.

**Profile & order note.** `Customer.name` (optional, ≤60, `GET/PATCH /api/me`) — the owner sees `name || email` (payload has both); customers only ever get their own masked email. `Order.note` (≤200) is the customer's special instructions, shown on the owner's card. Blank strings are stored as `NULL`. Customers see their last 20 orders via `GET /api/orders/mine`.

**Abuse limits on orders.** At most 30 lines per order, each item+size once (`OrderIn` in `features/orders/orders_schemas.py`) — every line is a DB lookup on the one event loop. At most `MAX_ACTIVE_ORDERS` (3) orders in progress per customer (`create_order`, 429), since cash on pickup makes prank orders free; cancelled/completed free a slot. The check runs before the order-number count, keeping the no-`await` numbering rule intact.

**Checkout key — no lost or doubled orders** (`Order.client_key`, nullable, unique per customer). The customer app sends a random `client_key` with every `POST /api/orders` (`checkoutKey()` in `customer/CustomerApp.jsx`, kept in `localStorage` under `CHECKOUT_KEY` until the order is confirmed; editing the cart drops it, logout clears it). If the server already has an order with that key for this customer it returns that order — before the paused / active-limit checks — instead of making a new one. Why: on the free tier the server often saves the order but the reply is lost (timeout, 502 while waking up); the customer then saw an error with a full cart, and "Place order" again made a duplicate. Now, after an unclear failure (no reply / timeout / 5xx) the app checks `GET /api/orders/mine` for its key, and every `loadOrders` (startup, `/ws/me` reconnect) empties the cart once its order shows up. Old apps send no key and behave as before.

**Owner's queue** (`GET /api/admin/orders`) = today's orders **plus any older order still in progress**, so an order placed before midnight doesn't vanish while it's being made (the card then shows its date, since numbers reset daily). Stats (`/api/admin/stats/today`): `cash_collected` = orders marked Done today (**Done means handed over and paid** — cash-on-pickup; `set_status` stamps `Order.completed_at`, nullable so `add_missing_columns` added it, and orders done before it existed fall back to `created_at`) — so an order placed at 23:50 and collected at 00:10 is the new day's cash, `orders` / `cancelled` placed today, `to_collect` and `active` (by status) over **all unfinished orders, any day**, `out_of_stock`, `accepting_orders`.

**Reports** (`GET /api/admin/reports?days=7|30`, owner; clamped 1–90; `admin/TodaySection.jsx`, the **Today** tab). `today` (orders / completed / cancelled / not_collected / cash / average, plus `in_progress` over all unfinished orders), `period` (the same over the last `days` stall days, today included), `daily` (cash by the day an order was marked Done — `completed_at`, falling back to `created_at` — and non-cancelled orders by the day placed), `top_items` (top 5 by quantity from **Done** orders only, at the prices saved on the order, with the `half` count), `hours` (non-cancelled orders placed per IST hour). Days and hours use `clock.to_ist` / `clock.days_start`. Bars are plain CSS — no chart library.

**Open / Paused** (`Setting` table, key `accepting_orders`; missing row = open). `PATCH /api/admin/store` (owner) flips it and broadcasts `{type: "store", accepting_orders, message}` on `/ws/menu` and `/ws/admin`; `GET /api/store` is public. While paused `create_order` refuses with **409** `PAUSED_MESSAGE` (checked on the server, so old tabs and old apps are covered); orders already placed carry on. The customer menu shows a banner and the cart disables Place order.

**Call the stall** (`Setting` key `stall_phone`; missing row = none). The owner sets the number on the Orders tab (`admin/StallPhone.jsx`, `PATCH /api/admin/store/phone`; spaces/dashes stripped, 10–13 digits with an optional `+`, blank removes it, a bad number is a **400** with a readable message — 422s only show a generic one). `GET /api/store` and every `{type: "store"}` broadcast carry `phone` (`store_service.store_status`). Customers see **📞 Call the stall** (a plain `tel:` link) with "Tell them: order #N" on every in-progress order in My orders, and it turns amber ("The stall hasn't started your order yet") once the order is still `placed` after 3 minutes — or until 10 minutes before the pickup time they chose (`notStartedYet` in `utils/pickup.js`). No number set = no button.

**Pickup time** (`Order.pickup_minutes`, nullable so `add_missing_columns` added it; `OrderIn` 0–120). At checkout the customer picks when they'll reach the stall — Now / 15 / 30 / 45 min (`PICKUP_OPTIONS`; default Now = 0; NULL = an older app that didn't ask). It is minutes after `created_at`; `pickupLabel` (`utils/pickup.js`) turns it into "Coming now" / "Coming ~6:45 pm" on the owner's card, the detail panel and the customer's order, and the owner's new-order push says "coming in 30 min". The owner's amber/red wait colours respect it: amber at `max(10, pickup)` minutes, red at `max(20, pickup + 10)`.

**Product feedback** (`Feedback` in `shared/models.py`, `POST /api/orders/{id}/feedback`, `GET /api/admin/feedback`). A customer rates the products of their own **completed** order — 1–5 stars + optional comment (≤300) per product, sent **once per order** (409 after; unique `(order_id, menu_item_id)`), only items in that order. Half/full of one product is one rating. `order_payload` carries `reviewed` and each item's `menu_item_id`. The customer is asked once when `/ws/me` reports `completed` (`customer/Feedback.jsx`), and completed orders show "Rate your food". The owner's read-only view is `admin/FeedbackSection.jsx` (averages + latest 100, full email). For showcasing later: `allow_public` is the customer's consent, `approved` (default false, unused yet) the owner's pick — **only ever show reviews with both true**, and show the name, never the email.

**OTP** (`backend/app/features/auth/otp_service.py`): 6 digits from `secrets`, compared with `hmac.compare_digest`, delivered by `deliver()` — through `backend/app/shared/mailer.py` (the single sender: `configured()` / `send_mail(to, subject, body, html=None)`, also used for the "order ready" email; with `html` it sends multipart/alternative, the plain text always included). The login-code email's HTML is `otp_email()` in `app/shared/email_templates.py` — table layout, inline styles, system fonts, hex colours (email clients ignore web fonts and may drop `<style>`; its only `<style>` is a phone-width media query on `mm-*` classes that shrinks padding and the code, so the inline full-size layout must keep working without it), logo from `MAIL_LOGO_URL` (default: the website's `/logo.png`). Delivery: SMTP when `SMTP_USER`/`SMTP_PASS` are set (Gmail locally; production uses Brevo's relay `smtp-relay.brevo.com` on port **2525** because Render's free tier blocks 25/465/587; `MAIL_FROM` is the visible sender and must be verified in Brevo), else (non-production only) logged to the console; production without SMTP returns 503. `OTP_DEV_MODE` (default false, ignored in production) enables the fixed code `123456`; `/api/auth/mode` returns `{dev_mode}` so the UI only shows the "use 123456" hint when it actually works. Limits: 3 sends / 10 min per email, and 5 wrong guesses per email across *all* codes in that window (resending doesn't reset it). Rows older than a day are deleted on each send. There is no per-IP limit (behind Render's proxy the IP is the proxy's).

**Menu editing (owner, `admin/MenuSection.jsx` + `admin/MenuItemForm.jsx`, `/api/admin/menu*`).** Add (`POST`), edit (`PATCH /{id}`), remove (`POST /{id}/remove`) / restore, and `DELETE /{id}` — **only for items never ordered** (409 otherwise). "Remove" sets `MenuItem.archived_at` (nullable, so `add_missing_columns` added it): the item leaves `GET /api/menu` and can't be ordered, but stays for past orders and reviews — **never hard-delete an ordered item**. `MenuItemIn` validates (name 2–80 / category ≤40, both space-squashed; whole rupees 1–10000; half < full); names are unique among items on the menu, case-insensitively (409), removed ones don't count, and restore re-checks. New items get `max(sort_order)+1` (end of their category; a new category goes last). Every change broadcasts `{type: "menu_changed"}` on `/ws/menu`; clients refetch (the customer cart re-prices / drops items via `reconcile`). `GET /api/admin/menu` lists all items with `archived` and `ordered`. CORS allows `DELETE` for this.

**Menu items and sizes.** Prices are `price_half` (nullable — null means the item has no half size) and `price_full`. Ordering `size: "half"` on an item without a half price is a 400. Categories are free-text strings ordered by `sort_order`; the seed data (`backend/app/features/menu/menu_seed.py`) is the stall's real menu from its poster (17 items, Momos first). `seed_menu` only fills an empty database; `replace_menu` (run by hand: `python -m app.features.menu.menu_seed` from `backend/`) makes an existing database match it — adds/updates by name, archives the rest, never deletes, safe to run twice. The customer menu's first chip / "Order Now" link follow the first category returned, not a hard-coded name.

**DB layer** (`backend/app/shared/database.py`): SQLite locally, Postgres in prod, chosen by `DATABASE_URL`. Tables are auto-created on startup (`Base.metadata.create_all`, in the app lifespan) and the menu is seeded then (dev only, see above) — order queries eager-load via `ORDER_LOAD` in `features/orders/orders_service.py`. `db.add_missing_columns()` (run right after `create_all`) `ALTER TABLE … ADD COLUMN`s any **nullable** model column an existing database lacks (and creates the model's indexes on the columns it added) — that is how `customers.name` / `orders.note` reached the local SQLite and Neon databases. It can't add NOT NULL columns, rename, or change types. There are no real migrations, so schema changes to existing prod data must be handled manually.

**Android app — customers and the owner** (Capacitor, `frontend/android/`, `frontend/capacitor.config.json`, guide in `docs/ANDROID.md`). The same React code and routes as the website, built with `npm run build:android` (= `vite build --mode android --outDir dist-android` + `cap sync`; Capacitor's `webDir` is `dist-android`, deliberately not the website's `dist`, so a website build can't be synced into the app — that shipped a customer login pointing at `localhost:8000` once). `.env.android` sets `VITE_APP_TARGET=app` (→ `IN_APP` in `constants.js`) and the production API URLs. In the app the Google button is hidden (`Login allowGoogle={!IN_APP}`: Google blocks sign-in inside web views); otherwise customers get the customer screens and the owner's login goes to `/admin`, exactly as on the web. **Android Back** (`src/hooks/backButton.js`, `@capacitor/app`): open panels/screens register `useBackButton(handler, active)`; Back runs the newest, and with none (main screen) minimizes the app. Any new full-screen panel/sheet must call `useBackButton(onClose)` (as `OrderDetail`, `MenuItemForm` and `Feedback` do), or Back leaves the app from inside it. Any new sheet or sub-screen must register one. The app's origin is `https://localhost`, which must be in `CORS_ORIGINS`. `frontend/android/` is committed (native project); its copied web assets are git-ignored. The website build (`npm run build`, Vercel) is unchanged. Every UI change needs a new APK for the app (bump `versionCode`). Handed-out APKs are **release** builds (`gradlew assembleRelease` with JDK 21 — Android Studio's JBR 25 fails with Gradle 8.14.3), signed via the git-ignored `frontend/android/keystore.properties` + `*.jks` (missing = unsigned APK; see docs/ANDROID.md Phase 4). `allowBackup="false"`: the saved JWT must never be backed up or restored to another phone.

**Push notifications (Android app, `backend/app/features/notifications/push_service.py`, `frontend/src/services/push.js`).** FCM HTTP v1 (using the already-installed `google-auth`, no Firebase SDK on the backend), sent as `BackgroundTasks` jobs that never raise — failures go to `t_log` as `TASK push`. Off unless `FIREBASE_SERVICE_ACCOUNT` (the whole service-account JSON) is set. A `push_tokens` row is one phone, owned by whoever logged in on it last (`email` + `customer_id`, re-registered on every launch via `POST /api/push-token`; logout posts `/api/push-token/remove` first). **Owner** phones (email in `ADMIN_EMAILS`) get new and customer-cancelled orders (`notify_admins`, channel `orders`). **Customer** phones get their own order's progress when the owner moves it — preparing / ready / completed ("tap to rate") / cancelled by the stall (`notify_customer` from `set_status`, `CUSTOMER_MESSAGES`, channel `status`, tag `my-order-{id}` so one notification per order is replaced) — never other customers' orders and never owner alerts. Data is `{order_id, kind}`; tapping opens the order (owner) or My orders / the rating sheet (customer) via `enablePush(onTap)`. 404/invalid-token responses delete the row. The app needs `frontend/android/app/google-services.json` (Firebase project, package `com.royanbrews.admin`) — without it the build still works but registration fails silently. Tests fake `push._client` (`tests/features/notifications/test_push.py`).

**Styling is token-driven.** All colors come from the Mr. Momo theme CSS variables (from the stall's poster: warm charcoal, yellow accent, pure-veg green) in `frontend/src/styles/index.css`; `tailwind.config.js` maps Tailwind color names (`bg1`, `accent`, `ink`, etc.) onto those vars. Change the theme in one place (the CSS `:root`), not in component classes. Fonts (Google Fonts, linked in `index.html`): `font-display` = Baloo 2 for headings, `font-body` = DM Sans; `.food-bg` is the food-doodle background (`public/food-doodles.svg`, drawn by `<FoodBackground />` in `components/ui.jsx`); food icons are in `components/icons.jsx` (`CategoryIcon` picks one by category name, a plate for unknown ones) and the hero steamer is `components/SteamerArt.jsx`. Login, the customer menu, the cart, My orders (`customer/Orders.jsx`: "In progress" cards with the tracker, then "Past orders"), the profile, the rating sheet (`customer/Feedback.jsx`) and the whole owner dashboard (Orders / Menu / Today / Reviews tabs) use them; the owner's add/edit item form and order detail panel still use the older glass style. The cart's bill is a sheet pinned to the bottom on phones (above `--sab`) and a cream receipt card beside the order from `md` up. Attention colours are tokens too: `danger` / `danger-soft` (tinted background), `warn` / `warn-soft` (orange, kept apart from the yellow accent: waiting orders, out-of-stock) and `star` (rating stars) — no hex or rgba in components. The logo is `frontend/public/logo.png`, shown through `<Logo />` in `components/ui.jsx` (it is drawn on white, so it sits on a white tile); the Android launcher icon / splash use the same artwork (`res/drawable-nodpi/ic_momo_foreground.png`, white background) and the small notification icon is a one-colour momo (`ic_stat_royan.xml` — old file name, new drawing).

**Edge-to-edge (transparent status/navigation bars).** `index.html` has `viewport-fit=cover` and `capacitor.config.json` sets `SystemBars` (`style: "DARK"` = light bar icons), so the page draws under both system bars in the Android app (and under notches in mobile browsers). `--sat` / `--sab` in `index.css` are the top/bottom bar heights (Capacitor's injected `--safe-area-inset-*`, else `env()`; 0 on desktop). `#root` is padded by them and a frosted strip sits behind the status bar. **Anything pinned to an edge must add them**: sticky headers `top-[calc(var(--sat)+0.5rem)]`, bottom bars/toasts `bottom-[calc(var(--sab)+…)]`, bottom sheets `pb-[calc(var(--sab)+1.25rem)]`. Removing `viewport-fit=cover` brings back Capacitor's plain grey bars.

## Gotchas

- `docs/ui-prototype-v2.html` is not part of the app — it is the old prototype of the glass layout (in its first, blue "Ocean" colours); the live colours are in `index.css`.
- Backend tests use a temp SQLite file (see `tests/conftest.py`), `SEED_MENU=false`, and create their own menu items via the `make_item` fixture — never rely on seeded ids/prices.
- Admin screens: `admin/AdminApp.jsx` — bottom tab bar **Orders / Menu / Today / Reviews** on phones (fixed, `z-40`, above `--sab`, `md:hidden`; the page reserves `pb-[calc(var(--sab)+6rem)]`, and anything else pinned to the bottom on admin screens, like the menu's Undo bar, must sit above it); from `md` up the same tabs plus mute / Log out are a sticky **sidebar**, and from `lg` the Orders queue shows **New / Preparing / Ready columns** (`COLUMNS`) instead of the filter chips (both are rendered; CSS hides one). The page root has class `admin-wide`, which widens `#root` to 1320px on `lg` (`#root:has(.admin-wide)` in `index.css`). Orders tab: Open/Paused switch, sound mute (`MUTE_KEY`, per device), the three numbers, out-of-stock warning (opens Menu filtered), New/Preparing/Ready filter chips, queue in-progress oldest first with amber ≥10 / red ≥20 min for placed/preparing, finished folded below; tap a card → `admin/OrderDetail.jsx`, which also exports the shared `StatusActions` buttons and time helpers. Android Back on any other tab returns to Orders. Reviews has an All / Low 1–2★ filter. `MenuSection` stays mounted on the other tabs (`visible` only hides its list), so a pending Undo bar survives a tab switch; leaving the Menu tab resets its out-of-stock filter. Menu editing lives in `admin/MenuSection.jsx` (the dashboard's Menu section). Shared frontend bits: `src/config/constants.js` (statuses/labels/icons/storage keys/`isActive`), `src/components/ui.jsx` (Back/BigButton/Field), `src/utils/alerts.js` (`beep`, `flashTitle`), `src/customer/Login.jsx` (used by customer and admin). Customer screens: login → menu ⇄ cart / orders / profile; the menu always shows a banner of in-progress orders. The menu's header sits in a solid `bg-bg1` sticky block from the very top (`-mt-[var(--sat)]`); its measured height is `--menu-head`, and the solid chips row sticks right below it. The active chip follows scrolling (an IntersectionObserver whose area is everything below the chips — a thin line gets skipped by fast flings) and stays locked to a tapped chip until its smooth scroll ends. My orders shows the date ("Mon 9 Nov · 12:59 pm", IST) for orders not placed today (`placedLabel` in `utils/pickup.js`). Log out asks first (customer and owner). The cart screen (`customer/Checkout.jsx`) edits lines itself (− / + / Remove via `changeLine` / `removeLine` in `CustomerApp`); every + is capped at `MAX_QTY` (50, the backend's `OrderItemIn.qty` limit).
- **No `window.confirm` / `window.alert`** — they show the site address and the system's colours (ugly in the Android app). Use `ask({ title, message, confirmLabel, cancelLabel, tone })` (→ Promise<boolean>; `tone` = accent / danger / warn) and `tell(message)` from `src/components/dialog.jsx`; `<DialogHost />` is mounted once in `main.jsx` (`z-[60]`, above sheets), and Android Back / Esc / a tap outside cancel.
- Tests must never send real email: `tests/conftest.py` blanks `SMTP_USER/PASS` (an empty env var beats `.env`). Tests that need SMTP "on" enable it *after* logging in (login codes use the mailer too).
- CORS origins come from `CORS_ORIGINS` (comma-separated). In production the frontend's exact Vercel URL — and `https://localhost` for the Android app — must be listed or the menu silently fails to load.
